한다. 그 파일은 `abc`/`dataclasses` 만 쓰는 순수 파이썬이라 ROS2 없는 Windows
에서 그대로 로드된다. 속도 상수도 `domain/task/motion.py` 에서 가져온다.

기다린다, 스스로 고치지 않는다"* 인데 Host 에 그 요청에 응답하는 코드가
없었다. 한 걸음(3cm / 3°)만 움직이고 GRASP 로 돌아가는 폐루프를 넣었다 —
`_judge_alignment` 주석의 *"관측 → 소이동 → 재관측"* 관례 그대로다.

**블리팅** — 렌더가 명령 주기를 결정하고, 명령 주기가 워치독을 결정한다.
즉 **화면 그리는 속도가 로봇의 안전 정지 판정을 좌우하고 있었다.**

## 3. 내일 정해야 할 것 두 개

### (a) `status_text` 를 줄일 것인가

블리팅 후 남은 렌더 143ms 중 **95ms 가 상태 텍스트 4줄**이다. 텍스트 비용은
폰트·bbox 와 무관하고 **줄 수에 비례**한다(4줄 72ms → 1줄 21ms).

2줄로 줄이면 ~40ms 를 벌어 워치독 여유가 1.23배 → 1.6배가 된다. 대신 화면에서
정보가 준다. **실측 Hz 를 보고 정할 것** — 여유가 충분하면 그냥 두면 된다.

> **2026-08-28 확정: 줄이지 않는다.** 실측이 ~7.0 Hz 로 워치독(3.33 Hz)의
> **2.1배** 였다. 어제 예상한 4.1 Hz 가 아니었으므로 40ms 를 더 벌 이유가 없다.
> 화면은 여전히 143ms 중 90ms 로 최대 비용이지만, 그건 여유가 남는 한 문제가
> 아니다.

### (b) geti 를 iGPU 로 바꿀 것인가

지금은 **CPU 가 기본값이고 그대로 두는 것을 권한다.** 근거:

- iGPU 추론이 1.6배 빠르지만(468.8 → 298.7ms) **명령 주기는 1.60 → 1.63 Hz 로
  변하지 않았다.** 병목이 CPU 부족이 아니라 렌더였기 때문
- 검출 레이트 1.7배는 **쓸 데가 없다** — 기물이 안 움직인다
- 모델 캐시를 켰으므로 로드 시간 손해는 사라졌다(30.3s → 3.1s). 언제든
  `--geti-device GPU.0` 로 쓸 수 있다

**바꿀 근거가 생기는 조건이었던 것:** ③번 A/B 에서 검출이 동등하고(문턱 0.6
근처가 안 갈리고) **동시에** 녹화 프로그램을 켠 상태에서 주기가 실제로 빨라질 때.

> **2026-08-28 확정: CPU 로 간다.** 두 번째 조건이 성립할 수 없게 됐다 —
> 녹화를 안 하기로 했고(전제 취소), 그것 없이도 CPU 로 이미 ~7.0 Hz 라
> 주기를 더 벌 이유가 없다. 병목은 여전히 렌더지 추론이 아니다.
> `--geti-device GPU.0` 는 플래그로 살아는 있다.
>
> **2026-08-28 추가 확정: GPU 는 비상용으로도 쓰지 않는다.** ③번 A/B 에서
> 같은 프레임인데도 **문턱 이상 검출이 8건 갈렸다**(§7). 첫 번째 조건인
> "검출이 동등한가" 가 깨졌으므로, 당일 무슨 일이 생겨도 디바이스를
> 바꾸는 것은 선택지가 아니다 — 바꾸는 순간 mission 이 보는 기물이 달라진다.

> 어느 쪽을 고르든 **리허설 시작 전에 정하고 그 뒤로는 바꾸지 말 것.**
> 디바이스를 바꾸면 리허설에서 확인한 것이 무효가 된다.

### 6-2. 버튼 4종 — 결함 있었고 고쳤다 (①)

**기능은 넷 다 정상이었다.** 로그로 확정: Mode(`-> MANUAL`) · Next(수동
모드에서 `SEARCH_TARGET → APPROACH_PIECE`, Next 없이는 안 일어나는 전이) ·
Prev(`APPROACH_PIECE → SEARCH_TARGET` 역방향 전이) · Reset. 창 닫기도 정상.

**시각 결함은 예상대로 있었다.** 마우스를 올리면 색이 변했다가 **바로 원래
색으로 돌아왔다.** Button 위젯이 hovercolor 로 바꾸고 `draw_idle()` 로 한 번
그려도, 다음 사이클의 `_blit()` 이 **버튼 색이 구워진 옛 배경**을 복원하면서
지워 버리기 때문이다.

**고친 방법 —** 버튼을 `_dynamic` 에 넣는 방법은 **쓰지 않았다.** 그러면 넷을
매 사이클 그리게 되어 렌더가 25.1 → 38.0 ms 로 는다(Agg 실측). 대신 `_blit()`
에서 **평소 색과 달라진 버튼만** 덧그린다:

```python
for button, idle in zip(self._buttons, self._button_idle_rgba):
    if button.ax.get_facecolor() != idle:
        self.fig.draw_artist(button.ax)
```

검증(Agg 오프스크린): 호버 색이 다음 사이클에도 유지 · 해제하면 정확히 복귀 ·
ready 표시등 안 가림 · **비호버 화면은 패치 전과 sha256 동일**(360,000px) ·
비용 비호버 25.0 ms(패치 전 25.1) · 호버 중 28.6 ms. 실기에서 유지 확인 완료.

### 6-3. 루프 Hz (②) — 예상보다 훨씬 좋다

`run_mission.py` 에 `--hz-every`(기본 20사이클) 를 넣어 단계별로 잰다.

```
[hz] 7.00 Hz  (143 ms/사이클)  캡처+ArUco 33  geti 6  FSM 12  화면 90 ms
```

3회 실행, 40+ 샘플에서 **6.5~7.9 Hz, 중앙값 ~7.0**. 어제 예상 4.1 Hz 가
아니었다. **워치독 3.33 Hz 대비 2.1배 여유.** 화면이 143ms 중 90ms 로 여전히
최대 비용인 것은 어제와 같다 — 병목의 위치는 그대로고, 여유가 있을 뿐이다.

### 6-4. 환경 함정 하나

`PYTHONUTF8=1` 이 필요하다. (파이프로 리다이렉트할 때 특히 잘 걸린다.)

### 결과: 동등하지 않다

| 항목 | 개수 |
|---|---|
| 문턱을 사이에 두고 갈린 검출 | 0개 |
| **CPU 에서만 문턱 통과**(GPU 가 놓침) | **5개** |
| **GPU 에서만 문턱 통과**(CPU 가 놓침) | **1개** |

- `(514,346)` 의 knight — 프레임 10·26 은 CPU 만, **프레임 24 는 GPU 만** 잡았다.
  한쪽이 일방적으로 나쁜 게 아니라 **양쪽이 각자 따로 흔들린다**
- 프레임 16 — 세 기물이 몰린 자리에서 라벨이 어긋났다
  (CPU knight 0.860 ↔ GPU box 0.851 · CPU box 0.846 ↔ GPU star 0.825)
- 프레임 3 의 rook **0.905** — CPU 는 확신 있게 잡았는데 GPU 는 40px 안에서
  아무것도 못 냈다. 애매한 축에도 안 드는 값이라 가장 무겁게 본 항목이다

### 대조군을 반드시 같이 볼 것 (이 판정의 근거)

`--devices CPU CPU` 로 **같은 프레임을 CPU 로 두 번** 돌렸다:

```
짝지어진 검출 301개 (라벨 일치 301 · 불일치 0)
confidence 차이 평균 +0.0000 · 최대 +0.0000
★ 모든 항목 0개  →  판정: 동등
```

**추론은 결정적이고 스크립트의 짝짓기(중심 40px)도 멀쩡하다.** 그러므로 위 8건은
짝짓기 오류나 프레임 흔들림이 아니라 **전부 디바이스 차이다.** 이 대조군 없이는
"기물이 몰려서 잘못 짝지어진 것 아니냐" 를 배제할 수 없으니, 다음에 이 A/B 를
다시 돌릴 일이 있으면 대조군도 같이 돌릴 것.

### 스크립트 판정 기준을 고쳤다

원래 판정식은 `diff_label == 0 and only_a == 0 and only_b == 0 and not flips`
였는데, `_boxes()` 가 **문턱과 무관하게 모든 annotation** 을 돌려주기 때문에
